# Poster Bot

Telegram-бот публикации постов одного владельца в один канал: отложенные посты,
почасовые слоты и своё время, безопасная отправка без автоматических
повторов, история и журнал (30 дней). Термины — [GLOSSARY.md](./GLOSSARY.md),
этапы и приемка — [PLAN.md](./PLAN.md).

Статус: ядро, UI, отправитель и опрос реализованы; базовая офлайн-приемка
закрыта. Добавлены карточки выбора часа и своего времени, предпросмотр
запланированного поста и ближайшие 12 публикаций в главном меню.
Последний независимый полный офлайн-прогон:
`.venv/bin/python -m pytest -o addopts='' -q` → `692 passed in 73.71s (0:01:13)`,
выход `0`. Независимые Dispatcher-probes подтвердили прямой ввод времени,
явный выбор завтрашней даты без очереди до подтверждения, главное меню,
приватный preview выбранного черновика и безопасный UI-«Рестарт».
Независимое read-only ревью: материальных дефектов нет, критерии согласованного
объёма выполнены. Reviewer тесты не запускал; это не полный security-аудит
и не живая приемка. Подробности проверок — в [PLAN.md](./PLAN.md).
Изменения пока не закоммичены и не отправлены в GitHub. 2026-10-22 с явного
разрешения владельца выполнен перенос в Docker: текущий код запущен, базовый
живой опрос Telegram проверен. Ручная приемка UI и отправки в канал ещё
не выполнена; полная приемка в production не заявляется.
Мишень канала можно также задать публичным `@channel-username`.

## Требования

- Python 3.10–3.14 (`pyproject.toml`: `>=3.10,<3.15`); локально проверено
  на 3.14.7 в `.venv`.
- aiogram 3.31.0 (закреплён). Импортируется только при живом `run`;
  `check` aiogram не загружает (закреплено тестом).

## Установка

```bash
python -m venv .venv
.venv/bin/pip install -e ".[dev]"
```

Для ручной установки зависимости одобрены владельцем и ставятся только
в локальный `.venv`. Альтернатива без host-venv — Docker ниже.

## Docker — текущий рабочий запуск, SQLite

2026-10-22 host-процесс штатно остановлен, согласованная резервная копия
импортирована и проверена; работает один poller сервиса `bot`.
**Рабочая БД теперь в томе `poster-bot-data`, не в каталоге `data` проекта.**
Прежний host-файл сохранён, но больше не обновляется и не является актуальной БД.
Резервная копия перед переносом:
`data/backups/docker-cutover-20261022T130050Z/poster_bot.sqlite3`.
Храните её закрытой от посторонних: она содержит приватные данные бота.

Требуются Docker Engine и Docker Compose **2.30.0 или новее**: `env_file`
использует `format: raw`. Команды выполняются из корня проекта с доступом
к Docker daemon. Подготовьте локальный `.env` по таблице «Конфигурация» и
[.env.example](./.env.example), без кавычек вокруг значений; ограничьте доступ
к нему. Compose передаёт его только в окружение контейнера, не в образ.
Числовой id канала и `@channel-username` поддерживаются как при host-запуске.

```bash
docker compose build
docker compose config --quiet
```

Сборка создаёт один образ `poster-bot:latest`; проект Compose — `poster-bot`,
сервис — `bot`. Проверка `config --quiet` проверяет конфигурацию Compose,
не Telegram и не БД. **Не выводите полный `docker compose config`: он может
раскрыть значения `.env`.** Сборка требует доступа к реестру образов и
источникам зависимостей; контейнер при живой работе — к Telegram.

Настройки из [Dockerfile](./Dockerfile), [compose.yaml](./compose.yaml) и
[.dockerignore](./.dockerignore):

- Официальная база Python 3.14 slim закреплена digest (проверенная сборка —
  Python 3.14.9). Установлены runtime-зависимости, без extra `dev`; база IANA
  `tzdata` включена. Обновление закреплённой базы — отдельное действие.
- Процесс работает от UID/GID `10001:10001`; корневая ФС read-only,
  `/tmp` — tmpfs 16 MiB, capabilities сняты, `no-new-privileges` включён.
  `init: true`, срок штатной остановки — 30 секунд; порты не публикуются.
- И БД, и singleton-лок принудительно размещены в `/app/data`:
  `/app/data/poster_bot.sqlite3` и `/app/data/poster_bot.lock`.
  Compose перекрывает соответствующие host-пути из `.env`.
  Именованный том `poster-bot-data` сохраняется между контейнерами;
  PostgreSQL-сервис не добавлен.
- `restart: "no"`: старт только вручную, автоматический рестарт после сбоя
  и автозапуск после перезагрузки хоста не настроены.
- Docker-логи: `json-file`, до 10 MiB на файл, до трёх файлов.
- Build context разрешает только `pyproject.toml` и Python-файлы пакета
  `src/poster_bot`; `.env`, host-данные и `.git` не передаются в сборку.
  Будущие ресурсы пакета, отличные от `.py`, нужно явно включать в allowlist.

### Управление работающим сервисом

Из корня проекта, с доступом к Docker daemon:

```bash
docker compose ps
docker compose logs --tail=100 bot
```

Логи просматривайте локально; не передавайте полный вывод, `.env` или токен.
Для диагностики используйте только безопасные поля из раздела
«Если меню отвечает медленно».

```bash
docker compose restart bot       # перезапуск процесса в существующем контейнере
docker compose stop bot          # штатная остановка без удаления БД
docker compose up -d bot         # ручной запуск остановленного сервиса
```

Это отдельные операции по необходимости, не последовательность для проверки.
`restart` не пересобирает образ и не перечитывает `.env`: окружение уже
сохранено в контейнере. После изменения `.env` пересоздайте сервис вручную:

```bash
docker compose up -d --force-recreate bot
```

Для применения обновлённого исходного кода вручную пересоберите образ и
обновите сервис (сборка требует сети):

```bash
docker compose up -d --build bot
```

Во всех случаях используется тот же том; не запускайте дополнительный
host-poller. Telegram-кнопка «Рестарт» обновляет только меню, не процесс,
образ или окружение. Автозапуск после перезагрузки хоста не настроен.

### Перед первым запуском на другом хосте: новая установка или перенос

> **ВНИМАНИЕ: не запускайте контейнер параллельно с работающим host-ботом.
> Для существующей установки нельзя просто запустить его с пустым томом:
> история, очередь и дедупликация не перенесутся, возможны дубли публикаций.
> Нужны отдельное разрешение владельца на переключение, остановка старого
> процесса, согласованная резервная копия и проверенный импорт до старта.**

При переносе оператор должен после остановки старого процесса получить
согласованный SQLite-снимок с учётом WAL, проверить восстановление и хранить
резервную копию **вне** рабочего тома. Простое копирование живого `.sqlite3`
без WAL небезопасно. В подготовленный том переносится вся БД: времена,
идентификаторы, `file_id`, inbox/offset, receipts и все пространства UI,
а не только посты. До старта нужно проверить целостность и полноту данных,
доступ UID/GID `10001:10001` и права каталога `0700`, файлов `0600`.
Существующие права приложение автоматически не исправляет.
Владелец должен разобрать уже назначенные публикации и неопределённые исходы,
учесть простой и риск дублей; догоняющей отправки нет. `flock` внутри тома
**не защищает** от host-процесса с другим файлом лока.

Для действительно новой установки импорт не нужен. После подготовки `.env`
и прав в Telegram (см. «Живой запуск»), либо после отдельно одобренного и
проверенного переноса, владелец вручную запускает **один** poller:

```bash
docker compose up -d
docker compose ps
docker compose logs --tail=100 bot
```

Не публикуйте полный лог; при диагностике передавайте только безопасные поля
из раздела «Если меню отвечает медленно», без `.env` и токена.
Для обычной остановки достаточно `docker compose stop bot`.
Если нужно также удалить контейнер и сеть без удаления тома:

```bash
docker compose down
```

**Не добавляйте `-v` к `down`: это удаляет том с БД.** Удаление данных требует
отдельного явного намерения владельца и проверенной резервной копии.
Том сам по себе не является резервной копией.

**Не восстанавливайте копию поверх БД работающего контейнера.** Восстановление
требует остановки единственного poller, новой согласованной копии текущей БД
и отдельного плана проверки данных/прав до старта. Снимок до cutover уже
не отражает последующую работу: откат может потерять inbox, историю попыток
и привести к повторной обработке или дублям. Старый host-файл не используйте
как способ быстрого возврата в production.

Проверены сборка и изолированные офлайн-запуски `check` с синтетическими
данными без сети. При разрешённом cutover выполнен
`docker compose up -d --no-build`: импорт совпал по байтам/хешу и числу строк всех 15 таблиц;
`quick_check`/`integrity_check` успешны, нарушений внешних ключей нет, схема v4.
Три ограниченные проверки живой работы подтвердили продвижение getUpdates
и heartbeat без наблюдавшихся ошибок polling/handler/tick или конфликта 409.
Это не проверка отправки в канал или ручная регрессия Telegram UI.
Контейнерный SIGTERM, failure injection и запуск после перезагрузки хоста
не тестировались; полный набор из 692 тестов повторно не запускался.
Независимое focused security-ревью финального build context завершено:
замечание устранено, подтверждённых материальных уязвимостей в объёме
упаковки не осталось. Reviewer тесты не перезапускал; это не
production-сертификация и не замена живой приемки.

## Конфигурация

Код читает только эти переменные окружения (имена — из `config.py`):

| Переменная | Значение | Для live-режима |
|---|---|---|
| `POSTER_BOT_BOT_TOKEN` | токен бота | обязателен: не пустой, не плейсхолдер, валидный синтаксически |
| `POSTER_BOT_OWNER_USER_ID` | числовой id владельца | обязателен: положительное целое |
| `POSTER_BOT_CHANNEL_ID` | мишень канала: числовой id (для каналов — отрицательный, вида `-100…`) или публичный `@channel-username` | обязателен: ненулевой числовой id либо валидный `@channel-username` (`@` обязателен; 5–32 символа, первая — буква, далее буквы/цифры/подчёркивание) |
| `POSTER_BOT_DB_PATH` | файл SQLite | опциональна, по умолчанию `data/poster_bot.sqlite3` |
| `POSTER_BOT_LOCK_PATH` | файл singleton-лока | опциональна, по умолчанию `data/poster_bot.lock` |
| `POSTER_BOT_TIMEZONE` | IANA-пояс | опциональна, по умолчанию `Europe/Moscow` |
| `POSTER_BOT_SLOT_START_HOUR` / `POSTER_BOT_SLOT_END_HOUR` | границы часовых слотов | опциональны, по умолчанию `0`/`23` (полные сутки), `0..23`, начало ≤ конца |

- [.env.example](./.env.example) — только плейсхолдеры; реальные значения
  в файл примера не попадают.
- `POSTER_BOT_CHANNEL_ID` допускает две формы мишени: числовой id чата и
  публичный `@channel-username` (публичный канал). Обе формы офлайн
  (в т.ч. `check`) принимаются по синтаксису без сети; `@username` резолвится
  в стабильный числовой id ровно один раз при живом старте — см. «Живой
  запуск». Числовая форма ведёт себя как раньше (без лишних вызовов).
- Авточтения `.env` нет (зависимости dotenv в проекте отсутствуют).
  Значения берутся из окружения процесса; необязательный файл передаётся
  флагом `--env-file` **до** подкоманды: `poster-bot --env-file .env check`.
  Формат файла: строки `КЛЮЧ=ЗНАЧЕНИЕ`; пустые строки, строки с `#` и без
  `=` пропускаются; пробельные края убираются; **кавычки не снимаются** —
  остаются частью значения; значения из файла перекрывают окружение
  процесса.
- Переменные под другими именами код не читает: если в вашем окружении
  токен лежит, например, под именем `TG_TOKEN`, бот его не увидит —
  используйте имена из таблицы выше.
- Ошибки конфигурации называют только имена переменных, никогда значения.
- Окружение задаёт лишь начальные настройки: пояс и часы слотов потом
  меняются в разделе «Настройки» бота (хранятся в БД) и уже
  запланированные публикации не переносят.
- Бот задаёт безопасные права только для создаваемых им путей: новые файл БД
  и лок создаются с правами `600`, новые каталоги — `0700`. Ранее созданные
  файлы и каталоги он не меняет — этот механизм не
  защищает существующие файлы. При желании владелец может вручную выставить
  права на конкретные доверенные пути (например, `chmod 600` отдельно на
  свой env-файл и файл БД); универсальные шаблоны и рекурсивные обходы
  не рекомендуются, эта команда здесь не выполняется.

## Офлайн-проверка (без сети)

```bash
.venv/bin/python -m poster_bot check          # или алиас --check
.venv/bin/python -m poster_bot --env-file .env check
```

Проверяет структуру конфига (допустимы dummy-значения), создаёт/мигрирует
файл SQLite и печатает, что мешает live-режиму, не падая из-за этого.
Сеть Telegram не используется, aiogram не импортируется. Выход `0`.
Форма `@channel-username` в `POSTER_BOT_CHANNEL_ID` тоже проходит офлайн:
проверяется только синтаксис, резолвинг — исключительно шаг живого старта.

`run` на плейсхолдер-конфиге отказывает до обращения к Telegram
(выход `3`, сеть не открывается).

## Живой запуск — только вручную

Текущая установка работает в Docker: используйте управление сервисом выше.
Host-команда ниже — только для отдельной разработки/новой host-установки,
**не для текущего production и никогда не параллельно с Docker**.

Предварительно (на стороне Telegram, бот это не проверяет заранее):

1. токен бота (BotFather);
2. владелец должен написать боту в личные сообщения (например `/start`) —
   бот отвечает только владельцу и только в приватном чате, остальным —
   молча;
3. бот добавлен в канал администратором с правом публикации; отказ
   канала из-за прав приводит к «отказу отправки» (см. «Исходы»).

Если вместо числового id указан `@channel-username`: при живом старте бот
один раз резолвит его через getChat в стабильный числовой id и принимает
только чат типа channel с отрицательным числовым id (групповой/личный чат
за этим именем отвергается). Отказ — выход `3` (в сообщении только имя
переменной и безопасная причина, без username и текстов Telegram), сессия,
лок и БД освобождаются, отправки не происходит. Числовой id используется
как задан — без вызова getChat. Проверка резолвинга — только тип чата,
это не проверка прав (права бота в канале по-прежнему на владельце, п. 3).
Если `@username` переименуют во время работы, ссылки, построенные по
закешированному username, могут устареть до рестарта; сами публикации идут
по резолвнуту числовому id и переименование не ломает.

```bash
.venv/bin/python -m poster_bot --env-file .env run
```

Команда выполняется из корня проекта, с настроенным локальным `.env`.
Если бот уже работает в терминале владельца, сначала нажмите там `Ctrl+C`
и дождитесь возврата приглашения оболочки, затем выполните команду выше.
**Не запускайте второй экземпляр и не удаляйте лок или БД ради перезапуска.**
Это инструкция только для host-варианта. В Docker новый код требует
пересборки образа, изменение `.env` — пересоздания контейнера (см. выше).
После запуска откройте `/start` или нажмите «Рестарт» для свежего меню.
Кнопка в Telegram не загружает новый код и не перечитывает `.env`.

- Второй экземпляр получает отказ (flock по `POSTER_BOT_LOCK_PATH`), выход `4`.
- Остановка: `Ctrl-C` (SIGINT) или SIGTERM — корректное завершение,
  лок и БД освобождаются, выход `0`.
- Автостарт намеренно не настроен — host-запуск и запуск Compose ручные.

Коды выхода: `0` — чистая остановка; `2` — ошибка структуры конфига или
аргументов; `3` — конфиг не годен для live (в т.ч. отказ резолвинга
`@channel-username`) / Telegram отверг токен;
`4` — лок занят другим процессом; `5` — непредвиденный сбой рантайма.

## UI владельца (кратко)

- После `/start` основное меню постоянно доступно под полем ввода:
  пять кнопок — «Создать пост», «Отложенное», «Контент-план», «Настройки»
  и «Рестарт» отдельной строкой под строкой с «Настройки».
  Это обычная reply-клавиатура, не inline-query-режим BotFather.
  «Рестарт» выполняет тот же сброс текущего UI, что `/start`: заново присылает
  клавиатуру и нижнюю главную карточку, не повторяя preview. Сохранённые
  отложенные посты и публикации не удаляет; процесс не перезапускает.
  «Отложенное» хранит посты без назначенной даты публикации, а не вводит
  новый статус. Старое название «Черновики» принимается со старой клавиатуры
  или текстом только от владельца в личном чате, но больше не отображается.
  При переходах бот отправляет новую служебную карточку с inline-кнопками
  внизу чата (после предпросмотра), сохраняет её id, затем пытается удалить
  прежнюю известную карточку. Правка на месте не переносила бы её вниз.
  При первой установке нужна отдельная подсказка: Telegram не совмещает
  reply- и inline-клавиатуру в одном сообщении. Каждый `/start` или «Рестарт» заново
  отправляет эту подсказку с клавиатурой и нижнюю карточку, даже после
  локальной очистки истории; прежнюю известную подсказку пытается удалить.
- Для чистоты личного чата бот пытается удалить `/start`, команды меню и
  принятый обычный ввод владельца (текст, медиа, ответы на запросы настроек
  и времени) только после устойчивого сохранения соответствующего ввода.
  Отклонённые и неподдерживаемые сообщения остаются с объяснением.
  Пересылки «как есть» остаются: **не удаляйте их до публикации**, иначе
  повторная пересылка не сработает; бот предупреждает об этом. После явного
  выбора «редактируемой копии», проверки её полноты и устойчивого сохранения
  бот может убрать её исходные пересылки. Неподдерживаемая или неполная копия
  отклоняется без удаления источников и потери возможности переслать «как есть».
  Удаление — best-effort, не очистка всей истории;
  предпросмотры бота и посты канала не удаляются.
  Устаревшая или повторно нажатая кнопка даёт только всплывающий ответ,
  не создавая карточку; принятый callback подтверждается до предпросмотра.
- «Настройки» → «Часовой пояс»: постраничный список популярных городов
  (Москва первая), «Все пояса IANA» из доступной локально базы, поиск
  сообщением с названием популярного города или частью IANA и ручной ввод
  (например `Europe/Moscow`). Текущий пояс отмечен `✓`; начальная страница
  содержит его. UTC-смещение показано на текущую дату и может меняться из-за
  DST; выбор пояса не переносит уже запланированные публикации.
- Содержимое: текст, фото, видео, mp3, альбом (2–10 фото/видео),
  пересланные сообщения. «Продолжить» завершает набор (буфер альбома
  переживает рестарт). Одиночный mp3 отправляется через `sendAudio`,
  не как недопустимая медиагруппа из одного элемента.
- Пересланное по умолчанию уходит «как есть» повторной пересылкой
  (шапка источника сохраняется); отдельной кнопкой — «редактируемая
  копия» с правками.
- «Следующий свободный час» открывает свободные часы выбранного дня
  (сначала сегодня в настроенном поясе), а не сразу назначает публикацию.
  Прошедшие и занятые минуты скрыты; часы — в настроенном диапазоне.
  «← День», «Сегодня», «День →» меняют дату; «‹ Часы» / «Часы ›» —
  страницы по 16 часов. Выбор часа → сводка → «Подтвердить публикацию».
  Если час стал недоступен, панель предлагает выбрать другой.
- На начальном экране выбора времени публикации можно
  сразу прислать `810`, не нажимая «Своё время»: откроется заполненная форма
  на **сегодня** в настроенном поясе. Если 08:10 уже прошло, время остаётся
  заполненным с предупреждением; выберите «Завтра» или другую дату явно.
  Автоматического переноса на завтра и постановки в очередь нет:
  нужны «Продолжить» → «Подтвердить публикацию». Допустимы все 10 форм
  времени ниже; принятый ввод сохраняется до best-effort удаления сообщения.
- «Своё время» открывает карточку: дата — сегодня в настроенном поясе,
  время ещё не выбрано; сразу пришлите время, нажимать «Время» сначала не нужно.
  Допустимы `810`, `0810`, `8-10`, `08-10`, `8:10`, `08:10`, `8.10`,
  `08.10`, `8 10`, `08 10` (все означают 08:10 выбранного дня).
  «Дата» отдельно принимает `ДД-ММ-ГГГГ`, например `29-10-2026`, или кнопки
  «Сегодня» / «Завтра»; старый формат `ДД.ММ.ГГГГ` также поддерживается.
  Поля меняются независимо. Затем «Продолжить» → сводка →
  «Подтвердить публикацию». Сообщение `29-10-2026 08:10` лишь заполняет
  оба поля, не ставит пост в очередь. Голое `ЧЧ:ММ` не переносится на завтра.
  Принятые значения сохраняются устойчиво до best-effort удаления ввода;
  ошибочный ввод остаётся. Прошлое, занятая минута и неоднозначное или
  несуществующее местное время при DST отклоняются без резервирования.
  После сетевого подтверждения callback бот заново читает часы перед
  выбором часа, проверкой формы и окончательным планированием/сменой времени/
  перепланированием: пересечение выбранной минуты во время ожидания — отказ.
- Выбор строки в «Отложенном» сразу отправляет свежий приватный предпросмотр,
  затем нижнюю карточку действий. Отдельная кнопка «Предпросмотр» позволяет
  повторить его; внутренние переходы, «Назад» и редактирование сами preview
  не вызывают. До и после подтверждения callback проверяются текущий контекст,
  черновик и версия UI/снимок содержимого; устаревший выбор preview не отправляет.
- «Предпросмотр» отправляет свежий пост владельцу в личку, не в канал;
  служебная карточка приходит после него внизу. У публикаций кнопка есть
  в статусах «запланирован», «на паузе», «пропущен»,
  «неопределённый результат» и «опубликован», но не при отправке.
  Проверяются текущая карточка, публикация, её версия и статус; устаревшая
  кнопка не отправляет preview. Предпросмотр не меняет содержимое, время,
  статус или резерв минуты и не удаляет forward-источники; при отказе
  можно повторить его с новой карточки.
- «Контент-план» показывает кликабельные строки в одну колонку, по 10 публикаций на
  страницу: `ЧЧ:ММ | значок статуса | текст или подпись`.
  Значки едины для дневных и главных строк: 🕒 — запланирован и ждёт отправки,
  ⏸ — на паузе, ⏳ — идёт отправка, ✅ — опубликован,
  ❓ — неопределённый результат, ❌ — пропущен (включая подтверждённый отказ
  отправки). Обычный запланированный пост не помечается ❌.
  Это краткий фрагмент фактически
  сохранённого текста/подписи (до 80 символов, пробелы нормализованы);
  без текста — тип содержимого. «← Пред.», «Сегодня», «След. →» меняют день;
  «Ещё ↓» и «↑ Сверху» переключают страницы (100 публикаций — 10 страниц).
  Размер страницы «Отложенного» и журнала прежний — 6 записей; главный список — 12.
  Текст нативных inline-кнопок
  центрирует Telegram: выравнивание влево ботом не задаётся.
  Явный клик по строке здесь или в ближайших 12 сразу отправляет свежий
  приватный предпросмотр, затем карточку деталей с действиями.
  Внутреннее открытие деталей, сохранение и «Назад» сами preview не вызывают;
  отдельная кнопка «Предпросмотр» остаётся. При начатой отправке открываются
  только детали, без preview.
- Главная карточка показывает первые 12 запланированных и приостановленных
  публикаций: порядок по UTC-времени (при равенстве — id), отображение в
  поясе владельца, кнопки открывают публикации с приватным preview.
  При непустом плане текст карточки — только «📅 Контент-план», без вступления
  и дублирующего текстового списка. Посты — кликабельные строки в одну колонку:
  `ДД.ММ ЧЧ:ММ | 🕒/⏸ | 📝 фактический текст или подпись`.
  При пустом плане остаётся сообщение «Нет запланированных публикаций.».
  Для типа содержимого используются обычные Unicode-значки 📝/📷/🎬/🎵/🖼/↪️.
  Значки и фрагменты нужны только для отображения:
  сохранённый и отправляемый пост не меняются. Это не кастомные emoji Telegram.
  Четыре основные команды не дублируются inline: они в нижнем reply-меню;
  inline остаётся «Журнал». При 12 публикациях это 13 строк кнопок.
  После устойчивого сохранения исхода отправки фон обновляет
  **ту же главную карточку** на месте в том же формате: опубликованная запись
  исчезает, 13-я занимает освободившееся место.
  Другие экраны и незавершённое редактирование фон не прерывает.
  Сбой обновления UI не повторяет отправку в канал; временные сбои UI имеют
  отдельные паузы повторов. Удалённую карточку фон заново не отправляет;
  после очистки истории используйте `/start` для свежей карточки.
- Редактирование публикации ставит её на паузу до повторного
  «Подтвердить публикацию». Чтобы отложить пост без срока, выберите
  «В отложенное» и подтвердите снятие: содержимое сохранится без даты
  публикации, назначенная публикация удалится, минута освободится.
  Это не «Пауза»: на паузе время остаётся назначенным, а после его истечения
  публикация становится пропущенной. Удаление поста убирает ссылки истории — в канале
  ничего не меняется (опубликованные посты не удаляются).
- Начатую отправку изменить нельзя.
- Опубликованный пост доступен только для просмотра и приватного preview
  (со ссылкой в канал, если сохранена). Редактировать или удалять уже
  опубликованные сообщения канала из бота нельзя.
- Токены кнопок расходуются до выполнения действия: при сбое бота в этот
  момент UI-действие/предпросмотр могут быть потеряны, устойчивый черновик
  сохраняется — можно переоткрыть черновик и повторить (exactly-once для
  UI-действий не заявляется).

## Кастомные emoji Telegram

Существующие entities сохраняют `custom_emoji_id` и смещения/длины UTF-16.
Но сохранение entities не даёт боту права отправлять такие emoji в любой чат.
По [правилам Bot API](https://core.telegram.org/bots/api#html-style), для
канала боту требуется дополнительный username, купленный на Fragment;
Telegram Premium владельца достаточно только для личных чатов, групп и
супергрупп, не канала. Успешный private preview не доказывает права в канале;
forward не заявляется обходом ограничений. Покупки и цены здесь не
проверялись, реальная отправка кастомных emoji не тестировалась.

## Отправка и исходы — честные ограничения

- У Bot API нет ключа идемпотентности и истории чата для бота.
  Прерванная/неподтверждённая отправка → статус «неопределённый
  результат»; автоматического повтора нет никогда.
- Catch-up нет: минута, начавшаяся во время простоя, считается
  «пропущенной»; только ручное перепланирование.
- Определённый отказ Telegram (лимиты содержимого, нет прав в канале) →
  публикация становится «пропущенной» с записью в журнал; перепланирует
  владелец.
- Уведомление о простое (> 120 с или есть затронутые публикации) сначала
  сохраняется в outbox и только потом доставляется: at-least-once —
  теоретически возможен дубль уведомления, потеря — нет.
- Медиа хранится как `file_id`: по Bot API их переиспользует тот же бот
  без скачивания. Поэтому «копия» переживает удаление исходного медиа
  в канале; «как есть» зависит от доступности пересланного сообщения в
  чате владельца с ботом — если его там удалить, отправка не пройдёт и
  исход разбирается вручную.

## Ручная проверка канала при «неопределённом результате»

Бот историю канала не видит, проверка только ручная:

1. откройте канал и найдите пост на запланированную минуту;
2. если пост есть — пришлите боту ссылку на пост
   (например `https://t.me/c/1234567890/42`, для публичного канала —
   `https://t.me/<username>/<message-id>`) или id сообщения числом →
   пост будет отмечен опубликованным;
3. если поста нет — «В отложенное» с явным подтверждением риска
   («Подтверждаю риск»): при повторной публикации сверьтесь с каналом,
   чтобы не получить дубль.

## Журнал

30 дней событий, без содержимого постов и секретов: отложенные посты,
планирование, попытки отправки и их исходы, простои, уведомления,
смена настроек.

## Если меню отвечает медленно

После ручного перезапуска проверьте `/start`, переходы меню и выбор пояса.
При сбоях опроса безопасная строка диагностики имеет вид:

```text
poll failed: code=transport_error class=TelegramNetworkError category=network duration_ms=1200 retry_seconds=1.0
```

Это пример формата, не результат живого замера. Записываются только код,
класс, категория, длительность запроса и ожидание повтора, без токена и
сырого текста исключения. Для временных ошибок опроса (`timeout`,
`transport_error`, включая ошибки сервера) ожидание — 1 → 2 → 4 с, далее
4 с; для остальных повторяемых API-сбоев — до 30 с. При 429 выдерживается
как минимум Telegram `retry_after`. Это повторы чтения getUpdates,
не повтор неопределённой публикации в канал.

Ранее наблюдался `transport_error`; короткий RTT getMe (около 0,1–0,3 с)
сам по себе не объясняет задержки getUpdates. Исправлены курсор опроса и
ожидание повторов; после исправления задержки владелец подтвердил быстрые
ответы в живом боте. Это не доказательство устранения сетевой причины и не
живая проверка последующих карточек, выбора времени и главного списка. Если после
перезапуска ошибки сохраняются,
передайте только указанные поля диагностических строк — не `.env`, токен,
полный лог или содержимое сообщений. Автоматический внешний мониторинг
не настроен.

## Что не гарантировано

- Офлайн-тесты (fake transport/fake clock) не гарантируют
  реальную скорость Telegram; живая проверка новых карточек времени,
  preview, главного списка, очистки ввода и `/start` ещё не выполнена,
  живая проверка `@channel-username` не подтверждена.
   Последний независимый полный offline-прогон: `692 passed in 73.71s (0:01:13)`,
   выход `0`. Дополнительные независимые probes и завершённое read-only ревью
   описаны в PLAN.md, §1; они не заменяют живую проверку.
- Офлайн-ревью базового состояния (независимое код-ревью и статический
  security-разбор) не подтвердило эксплуаттируемых уязвимостей и материальных
  блокеров, но это не полный аудит и не проверка живой сети; приемка в
  production не заявлена (PLAN.md, phase 6).
