# Poster Bot

Telegram-бот публикации постов одного владельца в один канал: отложенные посты,
почасовые слоты и своё время, безопасная отправка без автоматических
повторов, история и журнал (30 дней). Термины — [GLOSSARY.md](./GLOSSARY.md),
текущие задачи — [PLAN.md](./PLAN.md).

**Последняя проверенная серверная установка — `example-server`, не локальный
Docker.** После отдельного выпуска исправления валидатора канал был отклонён
при старте, бот безопасно остановлен. Для приватного канала владелец должен
отдельно определить числовой `POSTER_BOT_CHANNEL_ID` и права бота-администратора.
Это блокер конфигурации/старта, не исправленный этим дополнением и не повод
автоматически переносить `.env`. Текущее состояние сервера после возможных
ручных действий владельца здесь не перепроверено. Ниже — хроника переноса
2026-10-23, а не подтверждение работающего сейчас poller.

При переносе единственный poller был запущен в Compose-проекте `poster-bot` из
`/srv/poster-bot`: контейнер `poster-bot-bot-1`
(`31d47c389703…`), том `poster-bot-data`. Образ включает снимок рабочего
дерева на момент переноса (125 безопасных файлов, 53 в `src/`; это не Git
HEAD) с единым дневным планом и подписанной копией пересылки. Финальный
офлайн-прогон замороженных исходников — `1229 passed in 161.15s`, выход `0`
(`/tmp/opencode/unified-day-forward-release-pytest.log`); focused read-only

Серверный `compose.override.yaml` (`0600`) задаёт `restart: unless-stopped`;

отката: теряются inbox и попытки, возможны повторные эффекты.

## Docker — активный серверный runtime, SQLite

### Активный серверный runtime (2026-10-23)

Последняя проверенная серверная установка была заблокирована при старте
из-за канала (см. статус в начале). Следующее описание — снимок переноса,
не свежая проверка доступности. При переносе единственный poller был на
сервере `example-server` (SSH alias), в
каталоге `/srv/poster-bot`; Compose-проект `poster-bot`,
сервис `bot`, контейнер `poster-bot-bot-1` (`31d47c389703…`), том
`poster-bot-data`. Процесс работает от UID/GID `10001:10001`, корневая ФС
read-only; БД — в томе, не в локальном `data`. Серверный `.env` — `0600` у
`root`, каталог проекта `0700`; файл передаётся только в окружение
контейнера, не в образ и не в Git.

Снимок исходников — рабочее дерево, не устаревший Git HEAD `2c5d4ec`:
125 безопасных файлов (53 в `src/`) перенесены контролируемым копированием,
их хеши совпали. Локальный и серверный wrapper-образы имеют разные digest,
но слои конфигурации и root FS одинаковы — законное различие сборок.
Независимая security-проверка контейнера и metadata на этапе переноса завершена:
новых материальных проблем нет (это не полный аудит).

Проверка и обслуживание выполняются на сервере, не из локального проекта:

```bash
ssh example-server 'cd /srv/poster-bot && docker compose ps'
ssh example-server 'cd /srv/poster-bot && docker compose logs --tail=100 bot'
```

`logs --tail=100` выводится в ваш терминал: это приватные данные. Не
пересылайте полный лог, `.env` или токен; для диагностики передавайте только
безопасные поля из раздела «Если меню отвечает медленно».

```bash
ssh example-server 'cd /srv/poster-bot && docker compose restart bot'
ssh example-server 'cd /srv/poster-bot && docker compose stop bot'
ssh example-server 'cd /srv/poster-bot && docker compose up -d bot'
```

`restart` не пересобирает образ и не перечитывает `.env`. Серверный
`compose.override.yaml` (`0600`) задаёт `restart: unless-stopped`; Docker
daemon `enabled`/`active`. После загрузки хоста контейнер стартует сам, а
после намеренного `stop` остаётся остановленным до `up -d`. Это не
гарантирует питание и доступность хоста 24/7; физическая перезагрузка и
общий Docker daemon с шестью другими контейнерами не тестировались. Порты
приложения не публикуются; нужен исходящий HTTPS.

Изменение серверного `.env` — только владельцем; значения не выводятся и не
коммитятся. Обновляйте отдельную серверную копию, сохраняйте `0600`, затем
пересоздайте контейнер, чтобы новый процесс прочитал окружение:

```bash
ssh example-server 'cd /srv/poster-bot && docker compose up -d --force-recreate bot'
```

**Правило изменений:** локальные изменения не применяются к серверу сами.
`.env` переносится только отдельной явной командой владельца; серверный
файл нельзя заменять или синхронизировать автоматически. Исходники
переносятся контролируемым копированием и затем собираются на сервере.
Не запускайте локальный тот же бот, пока работает серверный poller.
Серверный `.env` уже был перенесён при переносе 2026-10-23 до этого правила.
Локальные `.env` и `src/poster_bot/ui/texts.py` — зона владельца;
документация их не перезаписывает, не читает значения и не откатывает.

Изменения кода не попадают на сервер сами: watcher/автодеплой не настроен.
После отдельной проверки и контролируемого переноса только нужных исходников
в серверный каталог (без `.env`) соберите и обновите сервис на сервере:

```bash
ssh example-server 'cd /srv/poster-bot && docker compose up -d --build bot'
```

Перед production-командами нужны отдельное разрешение владельца, решение
блокера канала, остановка единственного poller и согласованная резервная копия.
Старый образ после сохранения native-данных несовместим для слепого отката
(см. предупреждение в начале). Это сохраняет серверный override и том.
Образ этапа переноса содержит снимок исходников на момент переноса; локальные правки
после него требуют этой ручной операции. Пересборка требует сети. Источник
серверного образа — рабочее дерево, не Git HEAD; Git-коммит/push не
выполнялись.

**Резервные копии — только вручную; cron/автоматика не настроены.** Холодная
копия до первого серверного старта: на сервере
`backups/20261023T144646Z/poster-bot-data.tar`, локально
`data/backups/server-cutover-20261023T144646Z/poster-bot-data.tar`; SHA-256
идентичны, данные сверены по хешам всех 17 таблиц, integrity/quick_check — OK,
нарушений FK нет, схема v5. Храните копии приватно (`0600`). Старый локальный
образ, том и контейнер сохранены, но устарели: сервер уже принял новые inbox
и публикации. Не запускайте их и не восстанавливайте копию без остановки
сервера, свежей согласованной копии и сверки исходов — иначе возможны дубли.

`env_file` использует `format: raw`. На сервере команды выполняются из
`/srv/poster-bot`; локально — из корня проекта. `.env`
готовится по таблице «Конфигурация» и [.env.example](./.env.example), без
кавычек вокруг значений, с ограниченным доступом; Compose передаёт его только
в окружение контейнера, не в образ. Числовой id канала и `@channel-username`
поддерживаются как при host-запуске.

Локальная сборка ниже — только для разработки или новой установки, не для
управления сервером:

```bash
docker compose build
docker compose config --quiet
```

Сборка создаёт один образ `poster-bot:latest`; проект Compose — `poster-bot`,
сервис — `bot`. Проверка `config --quiet` проверяет конфигурацию Compose,
не Telegram и не БД. **Не выводите полный `docker compose config`: он может
раскрыть значения `.env`.** Сборка требует доступа к реестру образов и
источникам зависимостей; контейнер при живой работе — к Telegram.

Настройки из [Dockerfile](./Dockerfile), [compose.yaml](./compose.yaml) и
[.dockerignore](./.dockerignore):

- Официальная база Python 3.14 slim закреплена digest (проверенная сборка —
  Python 3.14.9). Установлены runtime-зависимости, без extra `dev`; база IANA
  `tzdata` включена. Обновление закреплённой базы — отдельное действие.
- Процесс работает от UID/GID `10001:10001`; корневая ФС read-only,
  `/tmp` — tmpfs 16 MiB, capabilities сняты, `no-new-privileges` включён.
  `init: true`, срок штатной остановки — 30 секунд; порты не публикуются.
- И БД, и singleton-лок принудительно размещены в `/app/data`:
  `/app/data/poster_bot.sqlite3` и `/app/data/poster_bot.lock`.
  Compose перекрывает соответствующие host-пути из `.env`.
  Именованный том `poster-bot-data` сохраняется между контейнерами;
  PostgreSQL-сервис не добавлен.
- `compose.yaml` задаёт `restart: "no"`; серверный `compose.override.yaml`
  меняет политику на `unless-stopped` (см. «Активный серверный runtime»).
  В локальной установке автозапуск после перезагрузки хоста не настроен.
- Docker-логи: `json-file`, до 10 MiB на файл, до трёх файлов.
- Build context разрешает только `pyproject.toml` и Python-файлы пакета
  `src/poster_bot`; `.env`, host-данные и `.git` не передаются в сборку.
  Будущие ресурсы пакета, отличные от `.py`, нужно явно включать в allowlist.

### Управление локальной установкой (неактивна)

Следующие команды относятся к остановленной локальной установке и приведены
для истории/разработки. Для production используйте команды на сервере выше.
Из корня локального проекта, с доступом к Docker daemon:

```bash
docker compose ps
docker compose logs --tail=100 bot
```

Логи просматривайте локально; не передавайте полный вывод, `.env` или токен.
Для диагностики используйте только безопасные поля из раздела
«Если меню отвечает медленно».

```bash
docker compose restart bot       # перезапуск процесса в существующем контейнере
docker compose stop bot          # штатная остановка без удаления БД
docker compose up -d bot         # ручной запуск остановленного сервиса
```

Это отдельные операции по необходимости, не последовательность для проверки.
**Не выполняйте `docker compose up -d` локально, пока сервер работает: это
создаст второй poller.** `restart` не пересобирает образ и не перечитывает
`.env`: окружение уже сохранено в контейнере. После изменения `.env` локально
пересоздайте сервис вручную:

```bash
docker compose up -d --force-recreate bot
```

Для применения обновлённого исходного кода в локальной разработке пересоберите
образ и обновите сервис (сборка требует сети):

```bash
docker compose up -d --build bot
```

Во всех случаях используется тот же том; не запускайте дополнительный
host-poller. Telegram-кнопка «Рестарт» обновляет только меню, не процесс,
образ или окружение. Локальный автозапуск после перезагрузки хоста не
настроен; серверный — `unless-stopped` (см. выше).

### Перед первым запуском на другом хосте: новая установка или перенос

> **Серверный перенос на `example-server` выполнен 2026-10-23; раздел
> остаётся процедурой для будущих отдельно одобренных установок/переносов.
> Не применяйте его к работающему серверу без окна и сверки данных.**

> **ВНИМАНИЕ: не запускайте контейнер параллельно с работающим host-ботом.
> Для существующей установки нельзя просто запустить его с пустым томом:
> история, очередь и дедупликация не перенесутся, возможны дубли публикаций.
> Нужны отдельное разрешение владельца на переключение, остановка старого
> процесса, согласованная резервная копия и проверенный импорт до старта.**

При переносе оператор должен после остановки старого процесса получить
согласованный SQLite-снимок с учётом WAL, проверить восстановление и хранить
резервную копию **вне** рабочего тома. Простое копирование живого `.sqlite3`
без WAL небезопасно. В подготовленный том переносится вся БД: времена,
идентификаторы, `file_id`, inbox/offset, receipts и все пространства UI,
а не только посты. До старта нужно проверить целостность и полноту данных,
доступ UID/GID `10001:10001` и права каталога `0700`, файлов `0600`.
Существующие права приложение автоматически не исправляет.
Владелец должен разобрать уже назначенные публикации и неопределённые исходы,
учесть простой и риск дублей; догоняющей отправки нет. `flock` внутри тома
**не защищает** от host-процесса с другим файлом лока.

Для действительно новой установки импорт не нужен. После подготовки `.env`
и прав в Telegram (см. «Живой запуск»), либо после отдельно одобренного и
проверенного переноса, владелец вручную запускает **один** poller:

```bash
docker compose up -d
docker compose ps
docker compose logs --tail=100 bot
```

Не публикуйте полный лог; при диагностике передавайте только безопасные поля
из раздела «Если меню отвечает медленно», без `.env` и токена.
Для обычной остановки достаточно `docker compose stop bot`.
Если нужно также удалить контейнер и сеть без удаления тома:

```bash
docker compose down
```

**Не добавляйте `-v` к `down`: это удаляет том с БД.** Удаление данных требует
отдельного явного намерения владельца и проверенной резервной копии.
Том сам по себе не является резервной копией.

**Не восстанавливайте копию поверх БД работающего контейнера.** Восстановление
требует остановки единственного poller, новой согласованной копии текущей БД
и отдельного плана проверки данных/прав до старта. Снимок до cutover уже
не отражает последующую работу: откат может потерять inbox, историю попыток
и привести к повторной обработке или дублям. Старый host-файл не используйте
как способ быстрого возврата в production.

При первоначальном переносе 2026-10-22 проверены сборка и изолированные офлайн-запуски `check` с синтетическими
данными без сети. При разрешённом cutover выполнен
`docker compose up -d --no-build`: импорт совпал по байтам/хешу и числу строк всех 15 таблиц;
`quick_check`/`integrity_check` успешны, нарушений внешних ключей нет, схема v4.
Три ограниченные проверки живой работы подтвердили продвижение getUpdates
и heartbeat без наблюдавшихся ошибок polling/handler/tick или конфликта 409.
Это не проверка отправки в канал или ручная регрессия Telegram UI.
При обновлении 2026-10-23 штатная остановка контейнера подтверждена
(выход `0`, OOM отсутствует); failure injection и запуск после перезагрузки
хоста не тестировались. Полный набор из 692 тестов ради первоначального
переноса повторно не запускался.
Независимое focused security-ревью финального build context завершено:
замечание устранено, подтверждённых материальных уязвимостей в объёме
упаковки не осталось. Reviewer тесты не перезапускал; это не
production-сертификация и не замена живой приемки.

5. Офлайн-preflight — только на изолированной копии: направить

9. Откат — только осмысленный: никогда слепо не восстанавливать до-переходную

## Конфигурация

Код читает только эти переменные окружения (имена — из `config.py`):

| Переменная | Значение | Для live-режима |
|---|---|---|
| `POSTER_BOT_BOT_TOKEN` | токен бота | обязателен: не пустой, не плейсхолдер, валидный синтаксически |
| `POSTER_BOT_OWNER_USER_ID` | числовой id владельца | обязателен: положительное целое |
| `POSTER_BOT_CHANNEL_ID` | мишень канала: числовой id (для каналов — отрицательный, вида `-100…`) или публичный `@channel-username` | обязателен: ненулевой числовой id либо валидный `@channel-username` (`@` обязателен; 5–32 символа, первая — буква, далее буквы/цифры/подчёркивание) |
| `POSTER_BOT_DB_PATH` | файл SQLite | опциональна, по умолчанию `data/poster_bot.sqlite3` |
| `POSTER_BOT_LOCK_PATH` | файл singleton-лока | опциональна, по умолчанию `data/poster_bot.lock` |
| `POSTER_BOT_TIMEZONE` | IANA-пояс | опциональна, по умолчанию `Europe/Moscow` |
| `POSTER_BOT_SLOT_START_HOUR` / `POSTER_BOT_SLOT_END_HOUR` | границы часовых слотов | опциональны, по умолчанию `0`/`23` (полные сутки), `0..23`, начало ≤ конца |
| `POSTER_BOT_SIGNATURE_MAIN_TEXT` / `POSTER_BOT_SIGNATURE_MAIN_URL` | метка и ссылка основной строки обязательной подписи | обязательны набором из четырёх полей: метка — непустая однострочная ≤64 симв.; URL — `https://` ≤512 симв. |
| `POSTER_BOT_SIGNATURE_PARTNER_TEXT` / `POSTER_BOT_SIGNATURE_PARTNER_URL` | метка и ссылка партнёрской строки обязательной подписи | те же требования, все четыре поля задаются только вместе |

- [.env.example](./.env.example) — только плейсхолдеры; реальные значения
  в файл примера не попадают.
- Обязательная подпись задаётся четырьмя полями сразу («всё или ничего»):
  `POSTER_BOT_SIGNATURE_MAIN_TEXT`, `POSTER_BOT_SIGNATURE_MAIN_URL`,
  `POSTER_BOT_SIGNATURE_PARTNER_TEXT`, `POSTER_BOT_SIGNATURE_PARTNER_URL`.
  Итоговая строка `main | partner` (метки — `text_link`-ссылки на
  настроенные HTTPS-URL) собирается ботом сама и стоит последней строкой
   каждого сообщения подписанной копии; в альбоме подпись едет в его подписи
   (caption). Нативная пересылка — явно выбранное исключение: наша подпись
   в неё не добавляется. При этом полная конфигурация подписи по-прежнему
   обязательна для живого старта бота.
- Все четыре поля заданы и валидны → планирование работает; заданы частично
  или невалидны → ошибка структуры конфига (и `check`, и `run` выходят `2`,
  ошибка называет только имена переменных, никогда значения); все четыре
  отсутствуют → офлайн-`check` проходит как раньше, но живой `run` отказывает
   ещё до создания бота и любого getChat с выходом `3`, даже если нужен только
   режим нативной пересылки.
- Подпись вшивается в замороженный план подписанной копии (новые — версия 3;
  сохранённые планы версии 2 поддерживаются без переформатирования):
  изменение `.env` влияет только на новые или перепланированные посты после
  пересоздания контейнера; уже замороженные планы публикуются со своей
  встроенной подписью.
- `POSTER_BOT_CHANNEL_ID` допускает две формы мишени: числовой id чата и
  публичный `@channel-username` (публичный канал). Обе формы офлайн
  (в т.ч. `check`) принимаются по синтаксису без сети; `@username` резолвится
  в стабильный числовой id ровно один раз при живом старте — см. «Живой
  запуск». Числовая форма ведёт себя как раньше (без лишних вызовов).
- Авточтения `.env` нет (зависимости dotenv в проекте отсутствуют).
  Значения берутся из окружения процесса; необязательный файл передаётся
  флагом `--env-file` **до** подкоманды: `poster-bot --env-file .env check`.
  Формат файла: строки `КЛЮЧ=ЗНАЧЕНИЕ`; пустые строки, строки с `#` и без
  `=` пропускаются; пробельные края убираются; **кавычки не снимаются** —
  остаются частью значения; значения из файла перекрывают окружение
  процесса.
- Переменные под другими именами код не читает: если в вашем окружении
  токен лежит, например, под именем `TG_TOKEN`, бот его не увидит —
  используйте имена из таблицы выше.
- Ошибки конфигурации называют только имена переменных, никогда значения.
- Окружение задаёт лишь начальные настройки: пояс и часы слотов потом
  меняются в разделе «Настройки» бота (хранятся в БД) и уже
  запланированные публикации не переносят.
- Бот задаёт безопасные права только для создаваемых им путей: новые файл БД
  и лок создаются с правами `600`, новые каталоги — `0700`. Ранее созданные
  файлы и каталоги он не меняет — этот механизм не
  защищает существующие файлы. При желании владелец может вручную выставить
  права на конкретные доверенные пути (например, `chmod 600` отдельно на
  свой env-файл и файл БД); универсальные шаблоны и рекурсивные обходы
  не рекомендуются, эта команда здесь не выполняется.

## Офлайн-проверка (без сети)

```bash
.venv/bin/python -m poster_bot check          # или алиас --check
.venv/bin/python -m poster_bot --env-file .env check
```

Проверяет структуру конфига (допустимы dummy-значения), создаёт/мигрирует
файл SQLite и печатает, что мешает live-режиму, не падая из-за этого.
Сеть Telegram не используется, aiogram не импортируется. Выход `0`.
Форма `@channel-username` в `POSTER_BOT_CHANNEL_ID` тоже проходит офлайн:
проверяется только синтаксис, резолвинг — исключительно шаг живого старта.

`run` на плейсхолдер-конфиге отказывает до обращения к Telegram
(выход `3`, сеть не открывается).

## Живой запуск — только вручную

Серверная установка обслуживается через Docker; последний проверенный старт
был заблокирован каналом (см. статус в начале). Для обслуживания используйте
серверные команды в разделе «Docker — активный серверный runtime» только
после отдельного согласования, не считая этот раздел разрешением на запуск.
Host-команда ниже — только для отдельной разработки/новой host-установки,
**не для текущего production и никогда не параллельно с Docker**.

Предварительно (на стороне Telegram, бот это не проверяет заранее):

1. токен бота (BotFather);
2. владелец должен написать боту в личные сообщения (например `/start`) —
   бот отвечает только владельцу и только в приватном чате, остальным —
   молча;
3. бот добавлен в канал администратором с правом публикации; отказ
   канала из-за прав приводит к «отказу отправки» (см. «Исходы»).

Если вместо числового id указан `@channel-username`: при живом старте бот
один раз резолвит его через getChat в стабильный числовой id и принимает
только чат типа channel с отрицательным числовым id (групповой/личный чат
за этим именем отвергается). Отказ — выход `3` (в сообщении только имя
переменной и безопасная причина, без username и текстов Telegram), сессия,
лок и БД освобождаются, отправки не происходит. Числовой id используется
как задан — без вызова getChat. Проверка резолвинга — только тип чата,
это не проверка прав (права бота в канале по-прежнему на владельце, п. 3).
Если `@username` переименуют во время работы, ссылки, построенные по
закешированному username, могут устареть до рестарта; сами публикации идут
по резолвнуту числовому id и переименование не ломает.

```bash
.venv/bin/python -m poster_bot --env-file .env run
```

Команда выполняется из корня проекта, с настроенным локальным `.env`.
Если бот уже работает в терминале владельца, сначала нажмите там `Ctrl+C`
и дождитесь возврата приглашения оболочки, затем выполните команду выше.
**Не запускайте второй экземпляр и не удаляйте лок или БД ради перезапуска.**
Это инструкция только для host-варианта. В Docker новый код требует
пересборки образа, изменение `.env` — пересоздания контейнера (см. выше).
После запуска откройте `/start` или нажмите «Рестарт» для свежего меню.
Кнопка в Telegram не загружает новый код и не перечитывает `.env`.

- Второй экземпляр получает отказ (flock по `POSTER_BOT_LOCK_PATH`), выход `4`.
- Остановка: `Ctrl-C` (SIGINT) или SIGTERM — корректное завершение,
  лок и БД освобождаются, выход `0`.
- Автостарт host-запуска намеренно не настроен; серверный Compose использует
  `unless-stopped` (см. «Активный серверный runtime»).

Коды выхода: `0` — чистая остановка; `2` — ошибка структуры конфига или
аргументов; `3` — конфиг не годен для live (в т.ч. отказ резолвинга
`@channel-username`) / Telegram отверг токен / отсутствуют все четыре поля
подписи (частично заданные или невалидные поля — ошибка структуры, выход `2`);
`4` — лок занят другим процессом; `5` — непредвиденный сбой рантайма.

## UI владельца (кратко)

Ниже — контракт текущих локальных исходников. Новые preview, редактирование,
нативная пересылка и исправления «Отмена»/«Назад» не выпущены на сервер;
полная проверка и ручная живая приемка не заявляются (см. статус выше).

- После `/start` основное меню постоянно доступно под полем ввода, три строки
  по две кнопки (пробел после значка — часть названия):
  - «✍️ Создать пост» | «🗂 Отложенное»;
  - «📅 Контент-план» | «⚙️ Настройки»;
  - «📒 Журнал» | «🔄 Рестарт».
  Это обычная reply-клавиатура, не inline-query-режим BotFather.
  `/start`, «Рестарт» и «Контент-план» открывают один дневной план:
  сегодня в настроенном поясе, все статусы, по 10 публикаций
  на страницу, с переключением дат и страниц. Возврат в главное меню,
  отмена верхнего уровня и прежние menu-callback тоже ведут в этот план.
  `/start` и «Рестарт» заново присылают клавиатуру, но не повторяют preview. Сохранённые
  отложенные посты и публикации не удаляет; процесс не перезапускает.
  «Отложенное» хранит посты без назначенной даты публикации, а не вводит
  новый статус. Названия без значков, включая старое «Черновики», принимаются
  со старой клавиатуры или обычным текстом только от владельца в личном чате.
  Точное совпадение такого текста — команда меню; пересланное сообщение с тем
  же текстом командой не считается и текущее состояние через меню не сбрасывает.
  При переходах бот отправляет новую служебную карточку с inline-кнопками
  внизу чата (после предпросмотра) и устойчиво записывает её id; прежняя
  известная карточка удаляется best-effort по устойчивому реестру выходов бота
  только после успешной отправки новой.
  Правка на месте не переносила бы её вниз.
  При первой установке нужна отдельная подсказка: Telegram не совмещает
  reply- и inline-клавиатуру в одном сообщении. Каждый `/start` или «Рестарт» заново
  отправляет эту подсказку с клавиатурой и нижнюю карточку, даже после
  локальной очистки истории; прежняя известная подсказка удаляется по той же
  устойчивой очереди (см. следующий пункт).
- Для чистоты личного чата бот пытается удалить `/start`, команды меню и
  принятый обычный ввод владельца (текст, медиа, ответы на запросы настроек
  и времени) только после устойчивого сохранения соответствующего ввода.
  В режиме набора содержимого отклонённые и неподдерживаемые обычные сообщения
  остаются с объяснением (об отклонённых пересылках — ниже). На служебных экранах
  ввод не на том этапе, включая
  неподдерживаемый, может удаляться best-effort только после доставки подсказки
  и устойчивой записи отдельной отметки отклонения. Это не принятие содержимого:
  повторная доставка такого сообщения не добавит его в пост. При отказе доставки
  подсказки или записи отметки удаление не разрешается.
   Пересылки «как есть» остаются: **не удаляйте сообщения-источники в личке
   владельца, пока их координаты нужны любому сохранённому посту, нативному
   плану или намерению отправки**, в том числе после публикации. Не очищайте
   историю лички целиком: preview не заменяет источник. После явного
  выбора «редактируемой копии», проверки её полноты и устойчивого сохранения
  бот может убрать только источники, больше не нужные ни текущему вводу,
   ни любому сохранённому посту, нативному плану или намерению отправки.
   При нечитаемом сохранённом содержимом источник
  также остаётся; бот поясняет возможную зависимость сохранённого поста.
  Проверка повторяется непосредственно перед удалением точного id входящего
  сообщения в личке владельца. Даже после последующего снятия зависимости
  автоматическая очистка такого сохранённого источника не запускается.
  Неподдерживаемая или неполная копия отклоняется без удаления источников
  и потери возможности переслать «как есть».
  Некорректные/неподдерживаемые пересылки и корректные пересылки не на этапе
  создания/редактирования могут удаляться только после доставки объяснения,
  устойчивой отметки отклонения (не приёма содержимого) и проверки отсутствия
  известных ссылок на источник. Текущая форма при вводе не на том этапе
  сохраняется; сбой объяснения или записи не разрешает удаление. Старые
  сохранённые forward-посты защищены и без квитанции приёма.
  Удаление — best-effort, не очистка всей истории и не обещание удалить все пересылки.
  Устаревшая или повторно нажатая кнопка даёт только всплывающий ответ,
  не создавая карточку; принятый callback подтверждается до предпросмотра.
- Бот отдельно и устойчиво (в БД, переживает рестарт) знает id только своих
  приватных выходов: предпросмотров (каждый элемент альбома по отдельности),
  служебных карточек и подсказки клавиатуры. Их удаление выполняется только
  на следующем переходе владельца и только после успешной доставки замены:
  старый предпросмотр и старая карточка удаляются лишь после отправки новой
  карточки; при отказе preview или сбое записи карточки прежние остаются
  видимыми.
  По замыслу в чате остаются одна подсказка клавиатуры, текущая карточка и
  текущий предпросмотр. Неудачные удаления повторяются с нарастающей паузой
  и с соблюдением Telegram `429`/`retry_after`; сообщения старше 48 часов
  больше не повторяются (Telegram может отказывать в их удалении). Текущие
  карточка, подсказка и предпросмотр защищены от удаления. Сбой очистки не
  отменяет и не повторяет уже выполненное действие. Сообщений без id в реестре
  бот не знает и никогда их не перечисляет и не удаляет: старые выходы бота
   в истории можно убирать вручную лишь без удаления нужных источников:
   forward-источники «как есть» защищены всеми сохранёнными зависимостями.
   Посты канала не удаляются; гарантия
  полной очистки прежней истории не заявляется.
- «Настройки» → «Часовой пояс»: постраничный список популярных городов
  (Москва первая), «Все пояса IANA» из доступной локально базы, поиск
  сообщением с названием популярного города или частью IANA и ручной ввод
  (например `Europe/Moscow`). Текущий пояс отмечен `✓`; начальная страница
  содержит его. UTC-смещение показано на текущую дату и может меняться из-за
  DST; выбор пояса не переносит уже запланированные публикации.
- Содержимое: текст, фото, видео, mp3, альбом (2–10 фото/видео),
  пересланные сообщения. «Продолжить» завершает набор (буфер альбома
  переживает рестарт). Одиночный mp3 отправляется через `sendAudio`,
  не как недопустимая медиагруппа из одного элемента.
- Для пересланного есть два явных режима: подписанная редактируемая копия
   («Создать копию с нашей подписью?») и нативная пересылка «как есть» без нашей
   подписи, с шапкой пересылки Telegram. Автоматического выбора/конверсии нет.
   Нативный режим принимает одну полную операцию: сообщение либо один полный
   альбом до 10 элементов, без усечения. После выбора нужны полный приватный
   preview и явное одобрение; назначение времени отдельно завершается
   «Подтвердить публикацию». Неполный/неподтверждённый preview не разрешает
   подтверждение. Доступность источника к моменту отправки не гарантируется.
- При наборе обычного содержимого каждый принятый текст, фото или видео
   обновляет полный подготовленный preview, не теряя прежний ввод.
- Начальный выбор времени сразу показывает 12 ближайших свободных часовых
  слотов из настроенного диапазона, при необходимости на следующих днях,
  плюс до трёх предложений по последним ручным временам. Совпадающие моменты
  объединяются, весь список отсортирован по времени; кнопок может быть больше
  12. Поиск часовых слотов ограничен сегодня и следующими 399 днями:
  если свободных слотов недостаточно, список короче. Метки показывают дату
  и настроенный пояс. Кнопки «Следующий свободный час» больше нет.
  «Выбрать день» открывает отдельный дневной список без расширения на другие
  дни; прошедшие и занятые минуты скрыты, часы — в настроенном диапазоне.
  «← День», «Сегодня», «День →» меняют дату; «‹ Часы» / «Часы ›» —
  страницы по 16 часов. Выбор часа → сводка → «Подтвердить публикацию».
  Если час стал недоступен, панель предлагает выбрать другой.
- На начальном экране выбора времени публикации можно
  сразу прислать `810`, не нажимая «Своё время»: откроется заполненная форма
  на **сегодня** в настроенном поясе. Если 08:10 уже прошло, время остаётся
  заполненным с предупреждением; выберите «Завтра» или другую дату явно.
  Автоматического переноса на завтра и постановки в очередь нет:
  нужны «Продолжить» → «Подтвердить публикацию». Допустимы все 10 форм
  времени ниже; принятый ввод сохраняется до best-effort удаления сообщения.
- «Своё время» открывает карточку: дата — сегодня в настроенном поясе,
  время ещё не выбрано; сразу пришлите время, нажимать «Время» сначала не нужно.
  Допустимы `810`, `0810`, `8-10`, `08-10`, `8:10`, `08:10`, `8.10`,
  `08.10`, `8 10`, `08 10` (все означают 08:10 выбранного дня).
  «Дата» отдельно принимает `ДД-ММ-ГГГГ`, например `29-10-2026`, или кнопки
  «Сегодня» / «Завтра»; старый формат `ДД.ММ.ГГГГ` также поддерживается.
  Поля меняются независимо. Затем «Продолжить» → сводка →
  «Подтвердить публикацию». Сообщение `29-10-2026 08:10` лишь заполняет
  оба поля, не ставит пост в очередь. Голое `ЧЧ:ММ` не переносится на завтра.
  Принятые значения сохраняются устойчиво до best-effort удаления ввода;
  ошибочный ввод на служебной форме может удаляться после доставки подсказки
  и устойчивой отметки отклонения, но исправленное значение нужно прислать
  заново. Прошлое, занятая минута и неоднозначное или
  несуществующее местное время при DST отклоняются без резервирования.
  После сетевого подтверждения callback бот заново читает часы перед
  выбором часа, проверкой формы и окончательным планированием/сменой времени/
  перепланированием: пересечение выбранной минуты во время ожидания — отказ.
- Перед окончательным «Подтвердить публикацию» бот присылает полный
  сохранённый стек частей, затем нижнюю карточку подтверждения. После успешной
  постановки в расписание — снова полный стек и нижнюю карточку со статусом
  «запланирован». Это preview **после планирования**, не после физической
  публикации в канал. Учитываются все элементы альбома, не только первый id.
  Если preview до подтверждения не удался целиком, кнопка подтверждения
  не предлагается: форма позволяет повторить просмотр через «Продолжить».
  Если preview после планирования не удался, назначение остаётся сохранённым;
  повторяют только «Предпросмотр», а не постановку в расписание.
- Выбор строки в «Отложенном» сразу отправляет свежий приватный предпросмотр,
  затем нижнюю карточку действий. Отдельная кнопка «Предпросмотр» позволяет
  повторить его; внутренние переходы, «Назад» и редактирование сами preview
  не вызывают. До и после подтверждения callback проверяются текущий контекст,
  черновик и версия UI/снимок содержимого; устаревший выбор preview не отправляет.
- «Предпросмотр» отправляет свежий пост владельцу в личку, не в канал;
  служебная карточка приходит после него внизу. У публикаций кнопка есть
  в статусах «запланирован», «на паузе», «пропущен»,
  «неопределённый результат» и «опубликован», но не при отправке.
  Проверяются текущая карточка, публикация, её версия и статус; устаревшая
  кнопка не отправляет preview. Предпросмотр не меняет содержимое, время,
  статус или резерв минуты и не удаляет forward-источники; при отказе
  можно повторить его с новой карточки.
- «Контент-план» показывает кликабельные строки в одну колонку, по 10 публикаций на
  страницу: `ЧЧ:ММ | значок статуса | текст или подпись`.
  Значки едины для дневных и главных строк: 🕒 — запланирован и ждёт отправки,
  ⏸ — на паузе, ⏳ — идёт отправка, ✅ — опубликован,
  ❓ — неопределённый результат, ❌ — пропущен (включая подтверждённый отказ
  отправки). Обычный запланированный пост не помечается ❌.
  Это краткий фрагмент фактически
  сохранённого текста/подписи (до 80 символов, пробелы нормализованы);
  без текста — тип содержимого. «← Пред.», «Сегодня», «След. →» меняют день;
  «Ещё ↓» и «↑ Сверху» переключают страницы (100 публикаций — 10 страниц).
   Размер страницы «Отложенного» и журнала прежний — 6 записей; главная — этот же дневной план.
  Текст нативных inline-кнопок
  центрирует Telegram: выравнивание влево ботом не задаётся.
   Явный клик по строке плана сразу отправляет свежий
  приватный предпросмотр, затем карточку деталей с действиями.
  Внутреннее открытие деталей, сохранение и «Назад» сами preview не вызывают;
  отдельная кнопка «Предпросмотр» остаётся. При начатой отправке открываются
  только детали, без preview.
- Фоновое обновление включается только после успешного показа дневной карточки
  и привязано к выбранным дате/странице, id карточки и версии UI.
  После сохранения исхода отправки редактируется **та же карточка**:
  опубликованная строка остаётся, её значок меняется на ✅.
  Учитываются версии публикаций; неизменный снимок не вызывает API-запроса
  и не создаёт новых токенов кнопок. Фон не отправляет новые карточки или preview.
  Выбранная календарная дата сохраняется и после полуночи; «Сегодня», `/start`
  и повторный вход в план выбирают сегодняшний день на момент действия.
  При смене пояса границы выбранной даты пересчитываются в новом поясе,
  сами времена публикаций не переносятся.
  Формы, набор/редактирование, детали и preview фон не подменяет.
  Сбой обновления UI не повторяет отправку в канал; временные сбои UI имеют
  отдельные паузы повторов. Удалённую карточку фон заново не отправляет;
   для свежей карточки используйте `/start`, не удаляя нужные источники.
- Редактирование публикации ставит её на паузу до повторного
  «Подтвердить публикацию». Чтобы отложить пост без срока, выберите
  «В отложенное» и подтвердите снятие: содержимое сохранится без даты
  публикации, назначенная публикация удалится, минута освободится.
  Это не «Пауза»: на паузе время остаётся назначенным, а после его истечения
  публикация становится пропущенной. Удаление поста убирает ссылки истории — в канале
  ничего не меняется (опубликованные посты не удаляются).
- Начатую отправку изменить нельзя.
- Редактирование копии: «Отредактировать текст» сохраняет медиа и заменяет только текст;
   «Отредактировать вложение» сохраняет текст и заменяет только медиа (новые подписи здесь
   отклоняются); «Отредактировать всё» собирает весь пост заново. Полный
   preview и отдельное подтверждение нужны до замены сохранённого содержимого.
   Нативный оригинал нельзя править по компонентам: можно явно согласиться
   на замену подписанной копией и прислать весь пост заново либо выбрать
   замену другой полной пересылкой «как есть» с новым preview и одобрением.
   Свежие «Отмена»/«Назад» выходят без сохранения кандидата; версии UI и
   редактируемого поста/публикации проверяются, старые кнопки не применяют правки.
- Опубликованный пост доступен только для просмотра и приватного preview
  (со ссылкой в канал, если сохранена). Редактировать или удалять уже
  опубликованные сообщения канала из бота нельзя.
- Токены кнопок расходуются до выполнения действия: при сбое бота в этот
  момент UI-действие/предпросмотр могут быть потеряны, устойчивый черновик
  сохраняется — можно переоткрыть черновик и повторить (exactly-once для
  UI-действий не заявляется).

## Кастомные emoji Telegram

Существующие entities сохраняют `custom_emoji_id` и смещения/длины UTF-16.
Но сохранение entities не даёт боту права отправлять такие emoji в любой чат.
По [правилам Bot API](https://core.telegram.org/bots/api#html-style), для
канала боту требуется дополнительный username, купленный на Fragment;
Telegram Premium владельца достаточно только для личных чатов, групп и
супергрупп, не канала. Успешный private preview не доказывает права в канале;
forward не заявляется обходом ограничений. Покупки и цены здесь не
проверялись, реальная отправка кастомных emoji не тестировалась.

## Обязательная подпись и составная публикация (2026-10-23)

Подписанные планы v2/v3 описаны ниже и сохраняют прежнее поведение.
Серверный этап 2026-10-23 включал формат v3; текущие локальные исходники
добавляют отдельный нативный режим v4 (ещё не серверный выпуск).

- **Подпись копии.** Каждое сообщение подписанной копии заканчивается обязательной
  строкой `main | partner`; метки — ссылки `text_link` на настроенные
  HTTPS-URL (см. «Конфигурация»). В альбоме подпись размещается в подписи
   (caption) альбома. Без настроенной подписи план копии не строится.
   Явно одобренная нативная пересылка не получает нашей подписи,
   составных частей и навигационных правок; это не автоматический fallback.
- **Пустая строка перед подписью (формат v3).** Одна часть:
  `тело\n\nmain | partner`; несколько частей:
  `тело\n\nЧасть 1 | Часть 2 | ...\n\nmain | partner`.
  У медиа без текста — только подпись, без начальных пустых строк.
  Разделители учитываются в лимитах; исходное тело и entities сохраняются
  в плане без потерь. Уже сохранённые планы v2 читаются, просматриваются и
  отправляются с прежними текстом, entities и разделителями: обновление кода
  само не меняет одобренные запланированные посты. Новый формат применяется
  при явном перепланировании или создании нового плана.
- **Набор содержимого.** Текстовые абзацы, присланные по одному,
  докумечиваются в пост (каждый принятый абзац добавляется к уже принятым,
  прежние сохраняются дословно); «Продолжить» завершает набор. Фото и видео
  образуют один упорядоченный альбом не более чем из 10 элементов; подписи
  элементов сворачиваются в тело поста в порядке присылания. Одиннадцатый
  медиаэлемент отклоняется: первые 10 остаются в посте, лишнее сообщение
  не добавляется и не удаляется из чата.
- **Планирование копий (новые подписанные планы версии 3).** Планировщик жадно пакует целые абзацы
  в части: текст никогда не режется посреди абзаца и ничего не отбрасывается.
  Бюджет текста — 4096 символов на часть, подписи альбома — 1024 (URL живут
  в entities и в бюджет не входят); из бюджета части уже вычтены навигационный
  футер и подпись. У много-частичного плана каждая часть несёт футер
  `Часть 1 | Часть 2 | ...` (у одиночной части футера нет). Абзац, который
  не помещается даже с минимальным футером, даёт запрос ручного разбиения:
  бот показывает длины абзацев («Длины абзацев (в символах): …»), фрагменты
  не создаются, содержимое сохраняется целиком — владелец разбивает текст
  сам.
- **Предпросмотр.** Владельцу приходит ровно тот замороженный стек частей,
  который будет отправлен, — не сводное одно сообщение. В предпросмотре метки
  футера обычным текстом: ссылки на посты приватного канала до публикации
  существовать не могут.
- **Подписанная копия пересланного.** Для этого режима нужна явная кнопка
   «Создать копию с нашей подписью?» — шапка источника не снимается
   автоматически. Альтернатива — явно одобренная нативная пересылка
   из раздела UI, без изменения оригинала. Согласие одноразовое,
  привязано к текущему снимку UI; устаревшее согласие не применяется к новому вводу.
  До согласия сохраняется полный кандидат копии: текст/подпись, entities со
  смещениями UTF-16 и все `file_id`, отдельно от координат оригинала.
  Входящая подпись длиннее 1024 символов (проверены 1025 и 2048) больше не
  отвергается только из-за исходящего лимита caption. После явного согласия
  и проверки полноты планировщик размещает целые абзацы в общей подписи медиа,
  остальные — в следующих текстовых частях; каждая часть получает нашу подпись.
  Исходящие лимиты не меняются: caption ≤1024, текст ≤4096, включая футер и
  подпись. Если абзац не помещается в текстовую часть, бот просит ручное
  разбиение: полный кандидат и оригинал остаются, слова не режутся и текст
  не усекается. Только пригодная полная копия после устойчивого сохранения
  может разрешить удаление оригинала — с проверками зависимостей из раздела UI.
   Старые forward-посты без плана не конвертируются и не получают нативное
   разрешение автоматически: нужен новый явный выбор и полный просмотр.
   Для восстановления подписанной копии бот предлагает повторную присылку.
  Нажмите «Создать копию: прислать заново», пришлите **весь** пост и явно
  согласитесь на подписанную копию, если присылаете пересылку. Завершите набор
  через «Продолжить». Полная копия и план сохраняются до замены исходного
  содержимого в том же post id с прежним временем создания; id публикации и
  назначенное время сохраняются. Завершение редактирования запланированной
  публикации ставит её на паузу до повторного подтверждения.
  «Заменить», «Оставить прежнее» и подтверждение подписи медиа сохраняют
  привязку к редактируемому посту/публикации и проверку версии, не создают новый пост.
  Если полную копию восстановить нельзя, исходный пост и источник остаются;
  нужен полный повторный ввод владельца, а не попытка получить историю через getMessages.
  Наследная неподписанная пересылка без плана по-прежнему не отправится в свою
  минуту и может стать «пропущенной». Неподписанного fallback-preview и обхода
  подтверждения нет: реальный отказ API при полном preview блокирует подтверждение.
   Нативный план v4 создаётся только через новый явный выбор, не из наследного
   planless-поста в его минуту. Старый бинарный файл не понимает новые
   native-снимки, планы, намерения и UI; предупреждение об откате — в начале.
- **Отправка и навигационные правки.** У Bot API нет атомарной публикации
  нескольких сообщений: части уходят по одной, намерение отправить каждую
  часть устойчиво записывается до любого вызова API. После подтверждения всех
  частей бот выполняет один проход навигационных правок: футеры частей
  редактируются ровно один раз, метки становятся ссылками на соседние части
  (ссылки строятся только из подтверждённых id; собственная метка части
  остаётся текстом, тела частей не меняются). Проход не повторяется: при
  частичной или полной неудаче правок публикация остаётся «опубликованной»,
  владелец получает уведомление проверить ссылки вручную, тела частей никогда
  не пересылаются.

## Отправка и исходы — честные ограничения

- У Bot API нет ключа идемпотентности и истории чата для бота.
  Прерванная/неподтверждённая отправка → статус «неопределённый
  результат»; автоматического повтора нет никогда.
- Catch-up нет: минута, начавшаяся во время простоя, считается
  «пропущенной»; только ручное перепланирование.
- Определённый отказ Telegram (лимиты содержимого, нет прав в канале) →
  публикация становится «пропущенной» с записью в журнал; перепланирует
  владелец.
- Уведомление о простое (> 120 с или есть затронутые публикации) сначала
  сохраняется в outbox и только потом доставляется: at-least-once —
  теоретически возможен дубль уведомления, потеря — нет.
- Медиа хранится как `file_id`: по Bot API их переиспользует тот же бот
  без скачивания. Поэтому «копия» переживает удаление исходного медиа
   в канале; «как есть» зависит от доступности пересланных сообщений в
   личке владельца. Read-only проверка локальных координат не проверяет
   удалённую доступность; даже полный preview не гарантирует будущую отправку.
   Источники нельзя удалять, пока они нужны любому посту, плану или намерению.
- Нативное сообщение/альбом отправляется одним `forwardMessages` после
   устойчивой записи намерения. Неполный ответ, таймаут или прерванный вызов —
   «неопределённый результат»: проверка канала вручную, без автоматического
   досыла, повтора или превращения в копию. Достоверный отказ — «пропущен»,
   также без автоматического повтора. Telegram может пропустить недоступный
   элемент альбома; одна операция не означает атомарность.
- Составная публикация: у стека частей атомарности нет. Отправитель
  останавливается на первом же отказе: если ни одна часть не получила
  подтверждения канала (ноль ack) и отказ достоверный — публикация
  «пропущена»; иначе — «неопределённый результат», часть стека могла уйти
  в канал. Автоматического продолжения или повтора нет никогда; проверка
  канала — ручная (см. предыдущий раздел).
- Сбой навигационной правки не меняет исход «опубликован»: владелец
  получает уведомление проверить ссылки в канале вручную; тела частей не
  пересылаются.
- Запланированный пост без плана (наследная копия, созданная до дополнения
  2026-10-23) в свою минуту отправке сначала автоматически нормализуется и
  замораживается в план с настроенной подписью — до вызова канала, текст и
  id поста не меняются. Что подготовиться не может (пересылки, пустое или
  невалидное содержимое), отказывается по fail-closed («план публикации не
  заморожен») и становится «пропущенным»; перепланирует владелец.

## Ручная проверка канала при «неопределённом результате»

Бот историю канала не видит, проверка только ручная:

1. откройте канал и найдите пост на запланированную минуту;
2. если пост есть — пришлите боту ссылку на пост
   (например `https://t.me/c/1234567890/42`, для публичного канала —
   `https://t.me/<username>/<message-id>`) или id сообщения числом →
   пост будет отмечен опубликованным;
3. если поста нет — «В отложенное» с явным подтверждением риска
   («Подтверждаю риск»): при повторной публикации сверьтесь с каналом,
   чтобы не получить дубль.

## Журнал

30 дней событий, без содержимого постов и секретов: отложенные посты,
планирование, попытки отправки и их исходы, простои, уведомления,
смена настроек.

## Если меню отвечает медленно

После ручного перезапуска проверьте `/start`, переходы меню и выбор пояса.
При сбоях опроса безопасная строка диагностики имеет вид:

```text
poll failed: code=transport_error class=TelegramNetworkError category=network duration_ms=1200 retry_seconds=1.0
```

Это пример формата, не результат живого замера. Записываются только код,
класс, категория, длительность запроса и ожидание повтора, без токена и
сырого текста исключения. Для временных ошибок опроса (`timeout`,
`transport_error`, включая ошибки сервера) ожидание — 1 → 2 → 4 с, далее
4 с; для остальных повторяемых API-сбоев — до 30 с. При 429 выдерживается
как минимум Telegram `retry_after`. Это повторы чтения getUpdates,
не повтор неопределённой публикации в канал.

Ранее наблюдался `transport_error`; короткий RTT getMe (около 0,1–0,3 с)
сам по себе не объясняет задержки getUpdates. Исправлены курсор опроса и
