# PLAN.md — Poster Bot

Бот публикации постов одного владельца в один Telegram-канал: черновики,
планирование по слотам, безопасная отправка, история и журнал.
Термины — в [GLOSSARY.md](./GLOSSARY.md).

Легенда: `[x]` — выполнено; `[ ]` — запланировано; `⛔` — заблокировано (ждёт решения владельца). На 2026-10-21 ⛔-позиций нет.

## 2. Согласованные функциональные требования (утверждены)

Владелец и канал:
- Один владелец, один канал публикации.

Содержимое поста:
- Типы: текст, фото, видео, смешанный альбом, mp3 (аудио).
- Публикация: forward источника как есть либо редактируемая копия источника.
- Без усечения содержимого и без разбиения на несколько публикаций: пост,
  не проходящий в лимиты, отклоняется с объяснением (точные лимиты — §6).

Поток подготовки:
- Continue → preview → confirm; черновик сохраняется до удаления.
- Отмена различает два действия: возврат в черновики и удаление.
- Редактировать можно только запланированную публикацию; редактирование
  ставит её на паузу до повторного подтверждения.
- Истекшая (пропущенная) публикация требует ручного перепланирования.
- Начатая/идущая отправка неизменяема.

Время:
- Почасовые слоты на весь день; часы начала и конца настраиваются.
- Пользовательские будущие минуты; минута уникальна; недавние вручную
  введённые времена предлагаются отдельно от слотов.
- Следующий свободный слот строго в будущем.
- Время публикации проверяется при confirm; прошедшее время отклоняется.
- Часовой пояс выбирается, по умолчанию Europe/Moscow.
- Смена часового пояса или настроек слотов не переносит существующие
  запланированные публикации.

Отправка:
- Никакого catch-up и никакого автоматического повтора неопределённой отправки.
- Пропущенная публикация и неопределённый результат — только ручные действия
  владельца.
- После переподключения — уведомление владельцу: границы простоя и список
  затронутых постов. Никакого иного самостоятельного мониторинга владельца
  нет; штатные уведомления об успехе/ошибке отправки — только в журнал.
- Неопределённый результат проверяется владельцем вручную в канале
  (процедура документируется): у Bot API нет истории чата, проверка — ручная.

Данные:
- Ссылки на опубликованные посты в истории живут до удаления поста.
- Черновики живут до удаления.
- Журнал событий: 30 дней, без содержимого постов и секретов.

## 5. Архитектура (технические решения в рамках утверждённого стека §3)

Отдельного owner-блокера по архитектуре нет: владелец одобрил стек и
dev-зависимости (§3) и указал приступать к работе силами субагентов (§7).
Решения ниже — реализация и развитие согласованных требований §2; их статус
указан явно, а приемка этапов — в §4.

- Claim публикации — compare-and-set в транзакции против конкурентного
  редактирования (реализовано, тесты phase 3–4; офлайн-приемка phase 6 закрыта).
- Устойчивая запись попытки отправки до вызова Telegram (pre-call intent, таблица
  `send_attempts`) — реализовано, тесты phase 4.
- Незавершённая попытка на рестарте = «неопределённый результат» — реализовано,
  тесты phase 4.
- Пропущенная публикация остаётся на паузе (реализовано).
- Singleton lock процесса: один экземпляр бота (реализовано, phase 0).
- Тесты: fake clock и fake transport, без сети Telegram (реализовано).
- Сохранённые (pending) обновления после переподключения обрабатываются
  идемпотентно: персистентная дедупликация по идентификатору апдейта плюс
  устойчивое состояние; на границе intake эффект привязан к source key
  (`chat:message`) и расходуется атомарно с переходом ui_effects/state —
  replay не порождает дублей (например, повторного альбома);
  pending-строки inbox пинят offset getUpdates, молчаливый
  сброс backlog не допускается (реализовано: `polling.py`, `ui/handlers.py`,
  `repo/inbox`, `repo/processed_updates`; тесты дедупликации и рестарта).
- Подтверждение (confirm) проверяет актуальность: состояние и выбранное время
  сверяются с текущим состоянием хранилища и требованием «строго будущее»,
  устаревшая версия проигрывает (реализовано, в том числе UI-путь confirm).
- [x] Замечания hardening закрыты (фиксы проверены по исходникам и тестам,
  повторное независимое ревью — без материальных блокеров):
  `transport.build_transport` использует `config.owner_user_id` (битый
  атрибут исправлен); гигиена логов — только имена классов исключений;
  права на создаваемые файл БД/лок (0600) и каталоги (0700); `repr` конфига
  без токена; редакция журнала и компакция inbox в live-runtime
  (tests/test_acceptance_final.py закрепляет их через `compose_live`/PollLoop).
- ℹ Задокументированные ограничения (не дефекты): токен callback-кнопки
  расходуется до эффекта — при сбое UI-действие/preview теряются, устойчивый
  черновик выживает, повтор — из черновика (exactly-once для UI не
  заявляется); recovery-уведомления — at-least-once, возможен дубль после
  сбоя, это не автоповтор отправки в канал (tests/test_acceptance_final.py).

## 6. Верификация первичных источников и статус открытых позиций

- [x] Детальные лимиты Telegram верифицированы по первичному источнику —
  официальная документация Bot API (https://core.telegram.org/bots/api):
  - `#sendmessage`: текст 1–4096 символов после разбора entities;
  - `#sendphoto` / `#sendvideo` / `#sendaudio`: caption 0–1024 символа после
    разбора entities; mp3 поддерживается `#sendaudio`;
  - `#sendmediagroup`: альбом из 2–10 элементов, смешивание фото и видео
    разрешено;
  - `#sending-files`: полученный ботом `file_id` переиспользуется тем же ботом
    без скачивания файла; `#getfile` отдаёт файлы до 20 МБ — обязательный
    локальный кэш медиа и принудительные скачивания в план не закладываем;
  - `forwardMessages`/`copyMessages` сохраняют альбомы, но автоматически
    пропускают недоступные элементы: результат полон только когда количество
    возвращённых сообщений совпадает со входом; несовпадение — неполный
    исход, ручная проверка, без автоматического повтора всей пачки;
    пропущенные сообщения источника не сопоставляются по возвращённым
    идентификаторам назначений;
  - у Bot API нет истории чата и ключа идемпотентности отправки — отсюда
    ручная проверка канала в §2.
